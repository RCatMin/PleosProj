# 0007. 경로 계산과 장소 검색을 우리 앱이 한다

- 상태: Proposed
- 날짜: 2026-11-06
- 대체: 0004, 0005

## 맥락

0004에서는 경로 계산, 회전 안내, 장소 검색을 Pleos 기본 내비에 맡기고, 0005에서는 실제 주행에서 경로선을 그리지 않기로 했다. 그렇게 만들어 보니 문제가 컸다.

- NaviHelper는 경로를 하나만 주고 경로선 좌표를 주지 않는다. 앱의 핵심인 "후보 경로의 위험도를 비교해 안전한 길을 고르기"를 실제 주행에서 할 수 없다.
- 경로를 요청하면 기본 내비 화면이 앞으로 나오고, 우리 앱이 다시 앞으로 오는 것을 안드로이드가 막는다.
- 장소 검색은 기본 내비 검색 화면을 여는 것만 된다.
- 에뮬레이터에서 기본 내비 위치가 움직이지 않아 실제 주행을 보여 줄 수 없다.

운전자가 보는 화면은 처음부터 끝까지 우리 앱이어야 한다. 검색, 경로 비교, 안내가 모두 우리 앱에서 이뤄지는 내비를 만든다.

## 결정

경로 계산은 우리 앱이 OSRM으로 한다. OSRM은 OpenStreetMap 데이터로 길을 찾는 오픈소스 엔진이고, 지금은 공개 서버(router.project-osrm.org)를 쓴다. 공개 서버 이용 수칙에 맞춰 요청은 1초에 한 번 이하로 보내고 같은 요청은 다시 쓰지 않는다.

- 후보 경로: 대안 경로를 함께 받는다. 시내 짧은 거리에서는 대안이 거의 오지 않아서, 출발지와 목적지를 잇는 선의 양옆에 경유 지점을 찍어 다른 길을 더 받는다. 서로 70% 넘게 겹치거나 가장 빠른 길보다 두 배 넘게 걸리는 길은 버리고 최대 3개를 남긴다.
- 위험도 비교: 0003의 계산을 그대로 쓴다. 시나리오 재생과 같은 코드(`routing/RouteComparer`)를 쓰고, 구간마다 지날 시각의 기상청 예보·특보와 ITS 돌발상황(통제·사고)을 넣는다.
- 안내: 고른 경로를 따라 FusedLocation 위치로 다음 회전과 남은 거리를 계산하고, 경로를 벗어나면 다시 계산한다. 회피가 필요하면 위험 지점 양옆에 경유 지점을 찍어 다시 계산한다.
- 지도에는 실제 주행에서도 경로선을 그린다.

장소 검색은 카카오 로컬 API(키워드 검색)로 한다. 지도는 그대로 MapLibre와 OpenStreetMap 기반 지도를 쓴다(0002).

NaviHelper는 핵심 흐름에 쓰지 않는다. 우리가 고른 경로를 기본 내비에도 넘겨 교통 정보와 주의 지점을 받는 방법은 나중에 다시 검토한다.

## 검토한 대안

카카오모빌리티 길찾기는 실시간 교통이 반영되고 한국 도로에 강하지만 상용 서비스라 이번에는 쓰지 않았다.

OSRM을 우리 서버에 직접 띄우면 이용 제한이 없지만 서버를 따로 운영해야 한다. 공개 서버에서 막히면 이쪽으로 옮긴다. 코드는 주소만 바꾸면 된다.

기본 내비 중심(0004)은 위 맥락의 문제로 접는다.

## 결과

실제 주행에서도 후보 경로를 위험도로 비교하고, 경로선이 있는 안내를 하고, 위험 지점을 피해 다시 계산할 수 있다. 에뮬레이터에서도 위치를 옮기면 안내가 따라 움직인다.

OSRM에는 실시간 교통이 없어서 시내 소요 시간이 실제보다 짧게 나온다. 공모전 심사의 Pleos SDK 활용 면에서는 NaviHelper를 덜 쓰게 된다. Vehicle, FusedLocation, TextToSpeech는 계속 핵심에 쓴다.

공개 서버를 실제 서비스에 계속 쓸 수는 없다. 서비스로 낼 때는 자체 서버로 옮긴다.
