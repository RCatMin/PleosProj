# 0004. 기본 내비와 역할 나누기

- 상태: Proposed
- 날짜: 2026-10-31

## 맥락

처음에는 지도, 경로 계산, 회전 안내를 모두 앱에서 만들 계획이었다. 그런데 공모전 설명회에서 내비게이션을 처음부터 다 만들 필요는 없고 NaviHelper 같은 SDK를 잘 활용하면 된다는 안내가 있었다. 심사 기준에도 Pleos SDK를 핵심 기능에 잘 썼는지가 들어 있다.

그래도 사용자가 보기에는 위험을 함께 보여 주는 내비게이션이어야 하므로, 앱 화면은 내비처럼 보여야 한다.

## 결정

경로 계산, 회전 안내, 장소 검색, 현재 위치 주소는 Pleos 기본 내비가 맡고, 앱은 NaviHelper로 그 값을 받아 온다. 기본 내비는 뒤에서 안내를 계속한다.

앱은 받아 온 값으로 내비 같은 안내 화면을 직접 그리고, 위험 판단과 경고, 경로 선택을 맡는다. 안전한 경로는 `requestRoute`나 `requestRouteWithWaypoints`로 기본 내비에 넘기고, 새 위험이 생기면 `addWaypoint`와 `requestReRoute`로 바꾼다.

에뮬레이터에서 확인한 바로는 NaviHelper에서 다음 값을 받을 수 있다.

- 출발부터 도착까지의 회전 안내 목록 (회전 종류, 구간 거리, 안내 문구)
- 목적지, 남은 거리와 시간
- 현재 위치와 주소
- 기본 내비 검색 화면에서 고른 목적지
- 막힘 구간, 교통 이벤트, 주의 지점

경로선 좌표는 받을 수 없다.

## 검토한 대안

모두 직접 만드는 방법은 2주 안에 안내 엔진까지 만들기 어렵고, 설명회 안내와도 맞지 않는다.

기본 내비 화면을 그대로 두고 앱은 경고만 하는 방법은 가장 가볍지만, 위험을 보는 내비라는 경험을 보여 주기 어렵다.

외부 길찾기와 검색 서비스로 직접 계산하면 기본 내비가 실제로 가는 길과 어긋날 수 있다.

## 결과

경로와 안내 품질은 기본 내비 수준을 그대로 쓰고, 개발 시간은 위험 판단과 화면에 쓸 수 있다. NaviHelper를 핵심 기능 전반에 쓰게 된다.

경로를 요청하면 기본 내비가 화면 앞으로 나오므로, 앱을 다시 앞으로 가져오는 처리가 필요하다. 경로선은 ADR 0005의 방식으로 해결한다.
