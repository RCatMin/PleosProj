# 0004. 기본 내비와 역할 분담 (방법 1)

- 상태: Proposed
- 날짜: 2026-10-31

## 맥락

- 10/27에는 지도·경로·회전 안내를 모두 앱이 직접 하기로 했다.
- 10/29 공모전 통합 설명회에서 주최 측이 "내비게이션을 하나부터 열까지 만들 필요는 없다. NaviHelper SDK로 목적지 설정·관리 등을 쓰는 등 SDK를 잘 활용하면 된다"고 안내했다. 심사 기준 3(기술 활용성)이 "Pleos SDK·API를 핵심 기능에 적절히 활용했는가"다.
- 그래도 사용자 경험은 "위험을 보는 내비게이션"이어야 해서, 앱 화면이 내비처럼 보여야 한다 (10/30).

## 결정

- **경로 계산, 회전 안내 계산, 장소 검색, 현재 위치 주소는 Pleos 기본 내비가 하고, 앱은 그 값을 NaviHelper로 받아 온다.** 기본 내비는 뒤에서 안내를 돌린다.
- **앱은 내비처럼 보이는 안내 화면을 직접 그린다** (지도는 ADR 0002). 위험 판단·경고·경로 선택은 앱이 맡는다.
- 안전한 경로는 `requestRoute` / `requestRouteWithWaypoints`로 기본 내비에 넘기고, 새 위험이 생기면 `addWaypoint`·`requestReRoute`로 바꾼다.

### NaviHelper로 받는 값 (10/30 에뮬레이터 확인, PLE-12)

| 필요한 것 | NaviHelper |
| --- | --- |
| 회전 안내 | `onTBTInfo`: 출발~도착 전체 목록 (회전 종류, 구간 거리, 안내 문구) |
| 남은 거리·시간 | `onDestinationInfo`, `onDrivingInfo`, `onRouteStarted` |
| 현재 위치·주소 | `onCurrentLocationInfo` |
| 장소 검색 | `requestNavigationScreen(SearchPlace)`로 기본 내비 검색 화면을 열고, 고른 결과를 이벤트로 받음 |
| 교통·주의 정보 | `RouteStateInfo.trafficStatus`(막힘·교통 이벤트), `onCautionPointInfo`(미끄러운 도로·안개 등) |
| 경로선 좌표 | **없음** → ADR 0005 |

## 검토한 대안

- 지도·경로·회전 안내를 모두 직접(10/27 결정) — 2주 안에 안내 엔진까지 만들기 어렵고, 설명회 안내와 심사 기준 3에 맞지 않는다.
- 기본 내비 화면을 그대로 쓰고 앱은 경고만(B안 초기형) — 개발은 가장 가볍지만 "위험을 보는 내비" 경험을 보여 주기 어렵다.
- 외부 길찾기·검색 서비스로 직접 계산(방법 2) — 기본 내비 경로와 어긋나고, 외부 서비스 도입이 필요하다.

## 결과

- 경로·안내 품질은 기본 내비 수준을 그대로 쓰고, 개발 시간을 위험 판단과 화면에 쓸 수 있다.
- NaviHelper를 핵심 기능 전체에 쓰게 되어 심사 기준 3에 유리하다.
- 경로를 요청하면 기본 내비가 화면 앞으로 나온다. 앱을 다시 앞으로 가져오는 처리가 필요하다.
- 경로선 좌표가 없어서 지도 위 경로선은 별도 방식이 필요하다 (ADR 0005).
- 에뮬레이터에서는 기본 내비 위치가 움직이지 않아 주행 중 갱신을 확인할 수 없다 (ADR 0005).
